Look up commands, flags, and configuration defaults for the `hulla` CLI. The npm package is named `hulla`, and its executable requires Bun.

## Commands and aliases

The command behavior below describes the upcoming CLI release. The published `hulla@0.1.0` does not include the new path flags or help behavior yet.

| Command                         | Alias              | Behavior                                                                                                         |
| ------------------------------- | ------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `hulla init`                    | `hulla initialize` | Write project configuration without configuring UI.                                                              |
| `hulla ui init`                 | `hulla ui i`       | Configure the UI source, targets, support files, and output paths.                                               |
| `hulla ui add [components…]`    | `hulla ui a`       | Configure UI on first use, then add or update component source and dependencies. Without names, open a selector. |
| `hulla ui remove <components…>` | `hulla ui r`       | Confirm removal of each named component directory.                                                               |
| `hulla api init/generate/dev`   | —                  | Existing legacy generator commands; not compatible with `@hulla/api` 2.0.                                        |

Bare `hulla`, `hulla ui`, and `hulla api` show help without initializing files. `--help`/`-h` works at every command level, and root `--version`/`-v` prints the installed version. Reserved `hulla install` (including aliases `i` and `add`) and `hulla init --clean` fail with an explanation instead of claiming success.

#### Command help

With `hulla` 0.2.0 or newer, use `--help` or `-h` on any command to see its usage,
aliases, subcommands, arguments, and options:

```sh
hulla --help
hulla init --help
hulla api generate --help
hulla ui add -h
```

Help exits with code 0 before loading project configuration or running a command.
It works outside a project and does not prompt, download, or write files. Aliases
show the canonical command's help. Placing the help flag before a subcommand also
shows the selected subcommand: `hulla --help ui add` and `hulla ui add --help`
show the same usage.

> [!WARNING] Older versions can execute commands when help is requested
> In `hulla` 0.1.0 and earlier, root help is a placeholder and nested `--help` can
> continue into normal command behavior. Check `hulla --version` before using
> nested help in an older installation.

## Shared options

| Option                    | Purpose                                                                          |
| ------------------------- | -------------------------------------------------------------------------------- |
| `--cwd <directory>`       | Select the app directory; default is the invoking directory.                     |
| `--project-config <path>` | Select a project config; default is `.hulla/hulla.json`.                         |
| `--config <path>`, `-c`   | Project-config alias for UI/setup; API commands use it for the generator config. |
| `--yes`, `-y`             | Prohibit prompts and accept confirmations, including overwrites and removal.     |
| `--help`, `-h`            | Show usage, options, and examples without running setup.                         |

Shared options can appear before or after subcommands. Relative paths other than `--cwd` resolve from the selected app directory. Differing values for the same shared option across command levels return an error.

```sh
hulla --cwd apps/web ui add button --yes
hulla ui add button --cwd apps/web --yes
```

These commands target the same app. Use a distinct `--project-config` when an API command also needs `--config` for generation.

### UI setup options

These options work on `hulla ui init` and `hulla ui add`, or before the subcommand on `hulla ui`:

| Option                     | Purpose or default                                              |
| -------------------------- | --------------------------------------------------------------- |
| `--source <url-or-path>`   | Replace saved sources with this registry during setup.          |
| `--framework <name>`, `-f` | Select the framework explicitly; also available on `ui remove`. |
| `--code-root <path>`       | Saved or detected code root; otherwise `src`.                   |
| `--components-root <path>` | Saved component root; otherwise `<code-root>/components`.       |
| `--copy-root <path>`       | Saved support-file root; otherwise the code root.               |

Paths must be project-relative directories. New nested paths are created; components must stay inside the code root. Explicit setup options on `ui add` rerun configuration. They do not relocate previously installed files. See [UI components](/docs/cli/ui) for the first-install workflow.

With `--yes`, give explicit component names and resolve ambiguous framework choices with `--framework`.

## Project config fields

`hulla init` writes `.hulla/hulla.json`; the schema also fills omitted optional defaults when loading it.

| Field                   | Required in file | Default or purpose                                                                                       |
| ----------------------- | ---------------- | -------------------------------------------------------------------------------------------------------- |
| `cli.scripts.add`       | Yes              | Package install command, e.g. `bun add`.                                                                 |
| `cli.scripts.addDev`    | Yes              | Development dependency command, e.g. `bun add -D`.                                                       |
| `cli.scripts.uninstall` | Yes              | Removal command, e.g. `bun remove`.                                                                      |
| `cli.scripts.upgrade`   | Yes              | Update command, e.g. `bun update`.                                                                       |
| `cli.cache`             | No               | Defaults to `true`; accepted in config but currently does not enable or disable cache reads/writes.      |
| `cli.cacheDir`          | No               | Defaults to `.hulla/.cache`, resolved from the selected project root; used for the UI source cache file. |
| `cli.logs`              | No               | Defaults to `true`; accepted in config but currently does not change logging behavior.                   |
| `configs.api`           | No               | `api.config.ts`.                                                                                         |
| `configs.ui`            | No               | `.hulla/ui.json`.                                                                                        |
| `$schema`               | No               | Editor/schema URL metadata.                                                                              |

`--project-config <path>` names the project JSON file and resolves once from the selected app directory. UI and project setup also accept `--config`. A custom config under `.hulla/` belongs to its parent project; other config files use their containing directory as the project root.

For UI settings, the config's directory is the project root, except that a config inside `.hulla/` uses its parent. `configs.ui` resolves from that root.

`hulla init` writes `.hulla/hulla.json` and records detected package scripts. Loading the file fills optional fields; an omitted `cli.cacheDir` resolves to `<project-root>/.hulla/.cache`. Relative custom cache paths also resolve from that root.

`cli.cacheDir` controls the location of cache data used by UI registry resolution; the UI source record file is `ui.cache.json` inside that directory. The `cli.cache` boolean is currently stored but not consulted by those cache paths. `cli.logs` is also stored, but its true/false value currently has no effect on logging.

## UI config fields

`configs.ui` points to the UI config; by default this is `.hulla/ui.json`, resolved from the project root. An absent UI file loads these defaults:

```json
{
  "version": 1,
  "sources": ["https://github.com/hulladev/ui/tree/master/generated"],
  "installs": [],
  "postAddUpdateStep": ""
}
```

Each install record written by `hulla ui init` includes `sourceUrl`, `libraryName`, `componentsRoot`, `copyFilesRoot`, and `frameworks`. A framework record includes `name`, `templatePath`, `outputPath`, and `tsconfigPath`. Optional fields are `composer` (`"cn"` or `"tailwind-merge"`), `codeRoot`, and `rootTsconfigPath`. `hulla ui init --yes` reuses a saved composer, or selects `cn` for a new install. The `postAddUpdateStep` string can run a formatter on changed files; a custom command uses the `{files}` placeholder.

Sources can be HTTP(S) URLs or local paths. Relative local paths resolve from the UI project root; `~` expands to the home directory. The default remote follows `master`; pin a tag or commit for repeatable inputs.

There are two caches: the project record at `<cli.cacheDir>/ui.cache.json`, and downloaded snapshots under `~/.cache/hulla/gittar`. Follow [UI components](/docs/cli/ui#update-and-remove-deliberately) to refresh them without clearing unrelated cache entries.

## Check installed integrations

Integration checks are part of the upcoming CLI release and are not included in `hulla@0.1.0`.
From a workspace root, `doctor` detects declared UI, style, API, db, and control integrations and
runs their individual checks. Use a namespace's `--check` to inspect just that integration:

```sh
hulla doctor
hulla ui --check --cwd apps/mobile
hulla api --check --cwd apps/server
```

`hulla style --check`, `hulla db --check`, and `hulla control --check` use the same runner.
No initialization or `--yes` is needed. The checks read local files without importing application
code, running package scripts, downloading registries, connecting to services, or changing files.

At a workspace root, checks include the root and its declared workspaces. `--cwd` selects an app
and its own workspaces. Detection uses declared dependencies and recognized config files; a
missing declared package fails, while an absent integration is skipped. Explicit config options
apply to the selected package, and child workspaces keep their own defaults.

| Check     | What it validates                                                                                                   |
| --------- | ------------------------------------------------------------------------------------------------------------------- |
| `ui`      | UI config, output paths, component/code-root containment, inherited TypeScript aliases, and native UI dependencies. |
| `style`   | Style packages, runtime entrypoints, and installed peer versions.                                                   |
| `api`     | API packages/adapters, runtime entrypoints, peer ranges, and optional generator config syntax.                      |
| `db`      | Database package, runtime entrypoint, peers, and optional `db.config.ts` syntax.                                    |
| `control` | Package installation, declared version, runtime entrypoint, and peers.                                              |

API runtime use does not require a generator config. Database package use does not require a
`db.config.ts`. Config syntax checks do not evaluate imports, exports, or values. These checks do
not validate connectivity, native binaries, rendering, stylesheet activation, or application types.
Continue running your application's builds and tests.

Results identify the package, directory, integration, and suggested fix. A failure returns exit
status `1`; passes, warnings, and skips alone return `0`. A failing integration does not stop the
remaining checks or sibling workspaces from reporting.

## Exit and error behavior

A successful command returns exit code 0. Parser, config, filesystem, registry, and task errors are reported to stderr and return 1. Interactive cancellation may exit with 0. Caught failures show the error and a command-help hint. It does not run the consuming application's build or tests after copying files; run those checks in your project or CI. See [Automation](/docs/cli/automation) for a repeatable add command.
