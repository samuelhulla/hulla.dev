Use `hulla ui` to copy components from a registry into your app. It installs their source files and dependencies; your app builds from those files without contacting the registry.

## Find a component's install name

Inspect the selected registry before installing. `list` reads family names, source exports, and filenames from the downloaded library; `search` is an alias that accepts the same query:

```sh
hulla ui list --framework react-native
hulla ui search text --framework react-native
hulla ui list --source ./my-registry
```

The output includes the library, framework, files, source exports, and an install command targeting that source. An export may belong to a family with a different name. An explicit `--source` inspects another registry without saving it. Discovery can download/cache a remote registry, but does not initialize the app, copy components, or install dependencies.

## Add your first component

Use `hulla@0.3.0` or newer for the commands below.

From an existing app directory, the first add configures the project and registry, then installs the named components:

```sh
hulla ui add button dialog
```

For a workspace app, stay in the repository root and select the app explicitly:

```sh
hulla ui add button dialog --cwd apps/mobile --framework react-native
```

The saved source and paths are reused on the next add. You can still run `hulla ui init` separately to review setup before installing components.

### Supply paths directly

Use setup flags to avoid the directory picker. This example runs against `apps/web`; the local registry path is relative to that app:

```sh
hulla ui init --cwd apps/web --source ./registry --framework react \
  --code-root src --components-root src/components/ui --copy-root src --yes
```

`--source` replaces the configured source list with that registry. `--code-root` controls `@/` imports, `--components-root` controls component output, and `--copy-root` controls support-file output. Defaults come from the saved install or detected code root, with components under `<code-root>/components` and support files under `<code-root>`.

Existing directories and new nested paths are accepted. Output roots must be project-relative; the component root must be inside the code root. Empty paths, control characters, files blocking a directory, and paths outside the project are rejected. Passing a source or root flag to `ui add` reruns setup before installing; changing roots does not move files from the previous destination.

## Configure the UI install

Run setup from the project root. The CLI reads sources from `.hulla/ui.json` (or uses its built-in source), detects supported frameworks, and plans file, alias, style, and dependency changes. It shows diffs before replacing existing configuration files.

```sh
hulla ui init
```

Choose the framework and destination paths that match your app. A registry advertises its available targets in `ui.config.ts`; select a revision that supplies the target you need. For the `react-native` target, follow [React Native components](/docs/ui/native).

For web targets, setup writes `lib/style.ts` with your chosen class composer. `cn` concatenates classes; `tailwind-merge` also resolves conflicting Tailwind utilities. Rerun `hulla ui init` to change the recorded choice. Native targets use React Native style objects. Native initialization installs the theme and tokens; component-specific support files arrive when their components are added.

> [!TIP] Load shared styles on every route
> In Astro, import the installed global stylesheet from a shared layout. The CLI doesn't configure your MDX component map; wire that through the renderer if you use Markdown.

## Add source files

Name the components explicitly so the same operation can be repeated in a script. Add `--framework` when the selected component exists in multiple configured framework targets.

```sh
hulla ui add --framework astro button dialog
```

Without names, interactive `add` opens a component selector. With `--yes`, supply one or more component names. It resolves each component's manifest, dependencies, aliases, and copy files. It reports changed file paths; review those diffs and run your app checks. Repeating the command with the same source revision should produce no meaningful source change.

If any requested family is unknown, `add` fails before copying component families and suggests matches from that registry. It does not silently substitute a family or skip a requested component. First-use setup validates after library/framework selection, before writing aliases or bootstrap files and installing dependencies; project configuration and empty destination directories may already exist.

### Use the project's formatter command

If the app defines a `format:files` script that accepts filenames, record that exact command during setup:

```sh
hulla ui init --post-add-command 'bun run format:files {files}' --yes
```

The command runs from the app root and is saved as `postAddUpdateStep`. `{files}` expands to shell-quoted file paths. Use `--post-add-command none` to disable it. Without the flag, setup offers formatter/custom choices; `--yes` retains the saved command or leaves the step empty. The CLI does not select a formatter based on dependency names.

Keep this command limited to the supplied files. The CLI also runs it on temporary incoming copies before comparing existing components, so formatting-only differences count as unchanged. A failed preview stops the add rather than falling back to a misleading diff.

### Share development tools in a workspace

Setup and component adds can reuse any registry-declared development dependency supplied by a declared workspace root. They verify an installed version against the required range, or reuse an identical declaration, an unconstrained requirement, or a compatible exact version when it is not installed. An incompatible or unverifiable requirement fails with the package and root manifest named; the CLI does not silently update that root.

Runtime dependencies remain app-local. Existing app declarations take precedence. The rule uses dependency metadata and workspace membership, without inferring which packages provide formatting or typechecking. A JavaScript registry without a TypeScript dependency or config template adds neither; selecting a typed registry does not convert its source to JavaScript.

### Install composed components

When a family imports another component family, `add` copies that source too, including further dependencies. With a native registry configured, install a date picker by naming its public family:

```sh
hulla ui add --framework react-native date-picker
```

The native date picker imports Button, Calendar, Drawer, and Select. The CLI includes those families once each, even when several imports need the same component. It keeps the dependency lookup inside the selected registry and framework; it cannot borrow a missing native component from the web target.

Existing dependency files receive the same overwrite review as explicitly requested components. Declining an overwrite keeps your customized file. External package dependencies go through the package installation step.

### Install support files as needed

The native registry installs `lib/theme.tsx` and `lib/tokens.ts` during setup. Adding Calendar installs `lib/date.ts`; adding Input installs `lib/text-input-style.ts`. Composed components receive the same support dependencies through their parts. Existing support files are preserved, including local edits, and relocated imports follow the configured support root.

Registry authors mark component-specific `copyFiles` entries with `onDemand: true`. The generator follows relative and `@/` imports, including transitive and type-only dependencies, and writes the component consumer list for the CLI. Entries without that setting are installed during setup. See [authoring support files](https://github.com/hulladev/ui/blob/master/docs/component-authoring.md#install-support-files-on-demand).

## Update and remove deliberately

To update copied files, select the intended registry tag or commit, rerun `hulla ui init`, then run `hulla ui add` for the components to update. Component files are updated with visible diffs. `ui add` keeps existing support files; review them alongside the selected registry source when updating component dependencies. See [Configuration](/docs/cli/configuration) for source settings.

`hulla ui add` can reuse a cached registry without checking whether its remote branch moved. To refresh it:

1. Select the intended source tag or commit in [configuration](/docs/cli/configuration).
2. Rerun `hulla ui init` to resolve that source.
3. Rerun `hulla ui add` for the components you want to update.
4. If the framework path is still stale, remove only `<cli.cacheDir>/ui.cache.json` and retry.

The default project record is `.hulla/.cache/ui.cache.json`. Downloaded snapshots live separately under `~/.cache/hulla/gittar`; [the downloader's cache policy](/docs/gittar/caching) explains that layer.

To remove one installed component, name it explicitly. The CLI asks before deleting its component directory; shared support files and dependencies may still serve other components and are retained conservatively.

```sh
hulla ui remove button
```

Inspect the resulting diff and run the application checks. Component removal does not promise to reverse every shared dependency, alias, or stylesheet change created during setup.

With `hulla ui remove --yes`, the deletion confirmation is accepted automatically. Supply the intended component names explicitly in automation.

## Keep the registry out of runtime code

Use a local registry while authoring a private component set, or a pinned remote source for shared consumption. The copied application source is the deliverable; do not import the registry into application code. This lets the app build after the CLI and registry are unavailable.
