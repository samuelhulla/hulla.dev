An application with live browser queries has three parts: your app, the persistent
`@hulla/db` service and PostgreSQL. Your framework deploys as usual; the service
maintains subscriptions and runs declared database functions.

| Component                            | What its host needs                                                           |
| ------------------------------------ | ----------------------------------------------------------------------------- |
| Application server using direct `db` | Node 22.18+ or Bun, native subprocesses and PostgreSQL connectivity           |
| Query service                        | A persistent Node/Bun process, native subprocesses and streaming HTTP ingress |
| PostgreSQL                           | Schema privileges and compatible connection/session behavior                  |
| Browser assets                       | Any suitable asset host with access to the service URL                        |

A container or VM can host the app and service together. Suitable function hosts
can run direct server operations; keep the subscription service persistent.
An edge isolate cannot run direct `db` if it forbids native processes, but it can
serve the frontend or call an application API. Next.js does not require Vercel.

## Use self-hosted or managed PostgreSQL

Supply the PostgreSQL connection URL in server config. A self-hosted instance and
a compatible managed endpoint use the same application API. SQLite services are
not PostgreSQL backends.

Check TLS, schema privileges, connection limits and session behavior against the
endpoint you will actually use. A transaction-pooler URL can behave differently
from a direct database URL; a PostgreSQL-compatible label alone does not establish
support for the package's session settings.

## Generate during the build

Install the matching SDK and native artifacts described in
[installation](/docs/db/installation#local-development-requirements). The migration
workflow below requires the updated development build. Generate during the build;
that build includes its own development runtime and compiler:

<DocsPackageManagerCommand
  commands={{
    bun: 'bun --bun hulla-db generate db.config.ts',
    npm: 'npx hulla-db generate db.config.ts',
    pnpm: 'pnpm exec hulla-db generate db.config.ts',
    yarn: 'yarn exec hulla-db generate db.config.ts',
  }}
/>

Include the config, schema, generated artifacts and their runtime dependencies.
Deploy the same schema and function artifacts to the app and service. Native
files live under `node_modules/@hulla/db/native/<os>-<arch>/`; retaining only the
JavaScript files is insufficient.

Framework bundlers must externalize/copy the package and retain its executables.
The [Next recipe](/docs/db/frameworks/next#keep-database-work-on-the-server) includes
asset tracing; other hosts use their normal packaging mechanisms. Use the bundled
executables for a supported target. Linux musl/Alpine, Linux arm64 and macOS x64
are not included in this release.

## Initialize fresh storage

Use a provisioning credential to initialize or verify storage. Node can run the
prepared runtime; Bun is not required for serving:

```sh
node node_modules/@hulla/db/dist/cli.js init db.config.ts
```

Initialization creates fresh storage or verifies an exact match. Use `migrate`
for a supported change to an existing database. These commands assume production
server environment variables are already supplied.

## Apply a schema change

Build the release first. During a maintenance window, stop application writers,
the query service and workers, then take a backup. With the new release's schema
and a provisioning credential, run:

<DocsPackageManagerCommand
  commands={{
    bun: 'bun --bun hulla-db migrate db.config.ts',
    npm: 'npx hulla-db migrate db.config.ts',
    pnpm: 'pnpm exec hulla-db migrate db.config.ts',
    yarn: 'yarn exec hulla-db migrate db.config.ts',
  }}
/>

`migrate` applies supported changes directly, without a confirmation prompt. Add
`--check` for a read-only plan. Repeating an already-applied migration leaves rows
unchanged. Unsupported changes fail instead of resetting storage; see
[schema authoring](/docs/db/schemas#change-an-existing-schema) for supported operations.

Production `serve` verifies storage; it never applies migrations at startup.
Previously connected runtimes reject a changed contract before further operations,
so start the matching application and service together after the migration succeeds.

If the migration connection is interrupted, run `migrate --check` to inspect the
result before proceeding. A committed upgrade is already current; a rolled-back
upgrade still has a pending plan. Applying the current schema again is harmless.

To reverse a committed upgrade, restore the backup into a separate database,
reapply grants, verify the data, and switch back to matching application artifacts.
That restore returns to the backup point; the command does not generate destructive
down migrations.

## Serve the prepared release

Start the matching application and persistent service with normal runtime credentials:

```sh
node node_modules/@hulla/db/dist/cli.js serve db.config.ts
```

`serve` verifies the installed contract and does not regenerate, watch source or
apply migrations. Terminate HTTPS at an ingress
that preserves streaming responses, allow the browser app's exact origin, and
verify credentials through the existing auth provider.

For same-origin browser calls, route `/functions/*` to the persistent service
and keep application/auth routes on the app server. Then browser configuration
can use the app's public origin. When the service has a separate origin, use that
service URL and configure CORS and credential transport for it explicitly. The
PostgreSQL URL remains private in both layouts.

## Share the database handle across requests

The generated server `db` lazily leases native database sessions and drains idle
ones. Reuse it across requests. Call `db.close()` at application shutdown, not
after each request, because another request can share that handle.

Transactions have an execution deadline, including waits between statements.
Keep slow external requests outside them. PostgreSQL also enforces statement and
idle-transaction bounds so a suspended application cannot hold a transaction
indefinitely.

A terminated application can lose a commit acknowledgement. Direct operations
do not replay that uncertain commit. Browser mutations use their existing
[confirmation flow](/docs/db/live-queries#when-a-mutation-response-is-lost).

## Validate the deployment you choose

Before routing production traffic, exercise native startup, concurrent requests,
reused instances, rollback, reconnects and live updates against that host and
database endpoint. Keep test namespaces and credentials separate from production.
Local package/build tests do not substitute for this endpoint-specific check.

Use the [framework recipes](/docs/db/meta-frameworks) for app entrypoints and the
[service guide](/docs/db/runtime) for listeners and budgets.
