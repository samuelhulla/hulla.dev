Put your database structure in `db/schema.ts`. `defineTable` describes fields;
the object keys passed to `defineSchema` are the table names used in queries.

```ts filename="db/schema.ts"
import { defineSchema, defineTable, v } from '@hulla/db/schema'

export const tasks = defineTable({
  title: v.string().min(1).max(200),
  completed: v.boolean().default(false),
})

export default defineSchema({ tasks })
```

The table gets a generated UUID `id`. An insert can omit `completed` to use its
default. Constraints such as `min`, `max` and `oneOf` validate values and become
storage constraints; they are not only TypeScript annotations. These bounds
apply to scalar columns. Nested JSON members use JSON shape validation; put
additional member rules in function validation or an explicit SQL check.

## Choose fields and defaults

Fields are required unless they have a default. `.nullable()` permits null but
does not make an insert optional:

```ts
const tasks = defineTable({
  title: v.string(),
  description: v.string().nullable().default(null),
  status: v.string().oneOf(['draft', 'published']).default('draft'),
})
```

Here `description` can be omitted or explicitly set to null. Without
`.default(null)`, a nullable field would still be required on insert. An update
ignores undefined values for known fields; null explicitly clears a nullable
field. Unknown fields throw on inserts and updates.

Generated UUIDs default to UUIDv7. For an explicit key, declare its field and name:

```ts
const projects = defineTable(
  {
    slug: v.string(),
    title: v.string(),
  },
  { primaryKey: 'slug' }
)
```

String keys need an explicit value unless you configure a generator. You can
split tables into modules and import them into `defineSchema`; that final object
remains the explicit set of registered tables.

## Infer rows, inserts and patches

Table declarations expose three type helpers:

```ts
type Task = typeof tasks.$inferSelect
type NewTask = typeof tasks.$inferInsert
type TaskPatch = typeof tasks.$inferUpdate
```

After generation, schema-bound aliases are also available:

```ts
import type { Row, Insert, Patch, Id } from './_generated/types'

type Task = Row<'tasks'>
type NewTask = Insert<'tasks'>
type TaskPatch = Patch<'tasks'>
type TaskId = Id<'tasks'>
```

Inserts account for defaults and key generation. Patches are partial assignments
and exclude the primary key. Generated IDs distinguish known references to
different tables while the database validates the underlying key representation.

## Reference another table

Use `v.id` for a foreign key. A string resolves a registered table name and avoids
module cycles; a table declaration can be passed directly too:

```ts
const projects = defineTable({ slug: v.string() }, { primaryKey: 'slug' })
const tasks = defineTable({
  project: v.id(projects, { onDelete: 'cascade' }),
  title: v.string(),
})

export default defineSchema({ projects, tasks })
```

`v.id('projects')` resolves the same registered key. Restrict is the default
deletion policy. Choose cascade when children should be deleted too, or set-null
on a nullable reference when they should remain. These are database-enforced
relationships, not automatic joins or embedded related objects.

One-to-many data uses a foreign key on each child. A many-to-many relationship
uses an explicit join table that you define. Query related rows with ordinary
builders; there is no implicit `include` or automatically generated join table.

## Declare uniqueness and indexes

A unique constraint expresses a data rule; an index is an explicit query aid:

```ts
const tasks = defineTable(
  {
    project: v.id('projects'),
    title: v.string(),
    completed: v.boolean().default(false),
  },
  {
    unique: { project_title: { fields: ['project', 'title'] } },
  }
).index(['project', 'completed'])
```

Ordering or filtering does not create an index for you. Declare indexes around
your actual queries. Unique constraints also provide eligible targets for
[`onConflict`](/docs/db/database#make-duplicate-inserts-deliberate).

Use a named SQL check for a rule involving several fields:

```ts
import { sql } from '@hulla/db/schema'

const ranges = defineTable(
  { low: v.int64(), high: v.int64() },
  {
    checks: (row) => ({ valid_range: sql`${row.low} <= ${row.high}` }),
  }
)
```

Interpolated fields and values remain separate from trusted SQL expression text.
Checks use PostgreSQL null semantics; a SQL check is not automatically converted
into a standalone function-input validator.

## Reuse table validation

The optional Zod adapter creates native strict schemas rather than requiring a
conversion for every field:

```ts filename="db/task-input.ts"
import { createInsertSchema } from '@hulla/db/zod'
import { tasks } from './schema'

export const newTask = createInsertSchema(tasks).pick({ title: true })
```

Use `newTask` as a mutation's input. Stored constraints such as title length are
preserved. Refinement callbacks can add application-only rules.
`createSelectSchema` and `createUpdateSchema` cover rows and patches. Validators
do not insert database defaults or silently coerce values. Resolve a schema with
`defineSchema` before adapting fields that use named foreign-key references.

## Change an existing schema

The [bundled development build](/docs/db/installation#local-development-requirements)
applies supported schema changes automatically when `dev` owns PostgreSQL. For an
external database, `migrate` applies the change and `migrate --check` previews it.
Use matching SDK and native executables from that build.

### During local development

Suppose `tasks` already contains saved titles. Add a defaulted field to its declaration:

```diff filename="db/schema.ts"
 const tasks = defineTable({
   title: v.string(),
+  archived: v.boolean().default(false),
 })
```

When `dev` owns PostgreSQL, saving this file regenerates and validates the code,
fills `archived` with `false` on existing rows, and restarts the service. Saved titles
and IDs remain intact. Leave the same development process running throughout.

The local database persists in `.hulla/postgres` across service reloads and dev
restarts. Invalid function code fails generation before a migration is applied.
An unsupported schema change leaves the database unchanged and the watcher waits
for corrected source.

### Apply a change to an external database

Setting `database.server.url` or `DATABASE_URL` tells `dev` to use your own database.
It does not initialize or migrate that database automatically. With the target
connection configured and a provisioning credential available, run:

<DocsPackageManagerCommand
  commands={{
    bun: 'bun --bun hulla-db migrate',
    npm: 'npx hulla-db migrate',
    pnpm: 'pnpm exec hulla-db migrate',
    yarn: 'yarn exec hulla-db migrate',
  }}
/>

The command compares your schema with the installed contract, applies supported
changes in one transaction, and prints `Schema migration applied.` It does not ask
for confirmation. An already-matching schema prints `Schema is already current.`
without repeating a backfill.

Use `init` once for fresh storage. After migrating an existing development database,
save a source file or restart `dev` so it starts against the new schema.

### Preview without changing data

Add `--check` to inspect the same plan without applying it:

<DocsPackageManagerCommand
  commands={{
    bun: 'bun --bun hulla-db migrate --check',
    npm: 'npx hulla-db migrate --check',
    pnpm: 'pnpm exec hulla-db migrate --check',
    yarn: 'yarn exec hulla-db migrate --check',
  }}
/>

A supported pending change lists the added tables, fields or references and prints
`No changes applied.` Check mode reports a plan; it does not fail merely because
supported changes are pending. Unsupported changes still fail with an error.

Commands use `db.config.ts` in the current directory. Pass another config path when
needed, for example `hulla-db migrate ./server/db.config.ts --check`.

### Supported schema changes

| Change                     | Behavior                                                    |
| -------------------------- | ----------------------------------------------------------- |
| Append a new table         | Creates the table with its declared indexes and constraints |
| Add a field with a default | Fills existing rows with that default                       |
| Add a nullable field       | Fills existing rows with null when no default is declared   |
| Reorder existing fields    | Preserves values and IDs by field name                      |
| Append a reference         | Validates existing values before committing                 |

Keep existing table and reference order. Renaming or removing tables or fields,
changing existing types/defaults/nullability, and changing existing indexes or
constraints require a separately reviewed data transformation. A required new
field without a default is rejected even for an empty table.

Backfilling a nullable field does not make future inserts optional. Use
`.nullable().default(null)` when callers should be able to omit it; see
[fields and defaults](#choose-fields-and-defaults).

Migration validation, column changes, backfills and metadata publication commit
together. Constraint or quota failures roll the operation back. Existing IDs,
committed mutation receipts and queued jobs are preserved.

For production deployment, follow the [migration and recovery sequence](/docs/db/deployment#apply-a-schema-change).
It covers provisioning credentials, backups, stopping writers and starting the
matching application release.
