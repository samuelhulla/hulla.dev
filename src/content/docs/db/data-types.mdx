---
title: Data types and codecs
description: Choose application representations for PostgreSQL values without losing precision or hiding conversions.
---

Table validators describe both a storage type and the value your application
reads and writes. Start with the default representations; choose an explicit
mode or codec when your application needs another one.

| Field                         | Application value                            |
| ----------------------------- | -------------------------------------------- |
| `v.string()`                  | `string`                                     |
| `v.boolean()`                 | `boolean`                                    |
| `v.number()`                  | Finite `number`, stored as double precision  |
| `v.int64()`                   | Safe integer `number`                        |
| `v.int64({ mode: 'bigint' })` | Exact `bigint` within the stored int64 range |
| `v.uuid()`                    | UUID `string`                                |
| `v.date()`                    | Calendar-date string, such as `'2026-10-21'` |
| `v.timestamp()`               | `Date` representing an instant               |
| `v.json()`                    | JSON-safe data                               |

Unsafe int64 number reads and writes fail instead of rounding. Bigint-mode sums
can exceed the stored int64 range, while individual stored values cannot.
Bigint-mode averages are decimal strings; ordinary numeric averages are numbers.
Custom field codecs do not transform aggregate output.

## Make date and timezone choices explicit

Use a date for a calendar day, and a timestamp for an instant. These have different
meanings even when a UI renders both as a date:

```ts filename="db/schema.ts"
import { defineTable, v } from '@hulla/db/schema'

const events = defineTable({
  day: v.date(),
  startsAt: v.timestamp(),
  precise: v.timestamp({ mode: 'string', precision: 6 }),
  localTime: v.timestamp({ withTimezone: false }),
})
```

Default timestamps use timezone-aware storage and millisecond Date values.
String mode preserves finer precision. Timezone-free timestamps default to a
clock-component string; they do not infer the machine's local timezone. Timestamp
precision is 0–6, with a default of 3; Date mode supports at most 3.
`v.date({ mode: 'date' })` and timezone-free Date mode are explicit alternatives.
Calendar Date mode uses the UTC calendar day; formatting it in another timezone
can display a different day. Incompatible precision/Date combinations reject
rather than lose information.

## Store structured JSON

A shape validates the whole JSON value, including nested objects and arrays:

```ts
const profiles = defineTable({
  settings: v.object({
    theme: v.string().nullable().optional(),
    tags: v.array(v.string()),
    appearance: v.object({ compact: v.boolean() }),
  }),
})
```

Bare `v.object(...)` and `v.array(...)` fields create validated JSON columns,
including nested types and codecs. `tags: v.array(v.string())` stores a JSON array.
Use `.nullable()` for a null column; `.optional()` belongs to nested object members.
Explicit `v.json({ ... })` remains available, as do `v.json()` for unrestricted data
and `v.json(...)` with column defaults.

`v.json<MyType>()` adds a TypeScript representation without a shape validator.
It still requires JSON-safe values, but does not prove the fields of `MyType`.
Undeclared properties in shaped objects throw. JSON updates replace the complete
column, avoiding ambiguous deep-patch behavior.

## Query JSON paths and arrays

Register the `profiles` table in your schema and regenerate. In application
server code, use the generated database and table references:

```ts filename="server/profiles.ts"
import { db } from '../db/_generated/server'
import { profiles } from '../db/_generated/tables'

const dark = await db.select(profiles).where('settings.theme', '=', 'dark')
const tagged = await db
  .select(profiles)
  .where(profiles.settings.tags, 'containsAny', ['editor', 'admin'])
```

Strings are relative to the selected table. A generated field reference also
preserves literal property names containing dots. Compound predicates use the
same callback helpers as ordinary columns:

```ts
const withSeveralTags = await db
  .select(profiles)
  .where(({ gte, arrayLength }) => gte(arrayLength(profiles.settings.tags), 2))
```

Null and presence checks have distinct jobs:

```ts
const absent = await db.select(profiles).where('settings.theme', 'not exists')
const present = await db.select(profiles).where('settings.theme', 'exists')
const nullOrAbsent = await db
  .select(profiles)
  .where('settings.theme', 'is', null)
```

`exists` tests member presence, including a present null. `is null` matches both
missing and null members; `is not null` requires a present, non-null value.
`= null` and `!= null` normalize to those same null checks. The three-argument
`where(path, 'exists', false)` is equivalent to `where(path, 'not exists')`.
Array operators include `contains`, `containsAny`, `containsAll` and `containedBy`;
use forms such as `'not contains'` for negation or callback `not(...)`.

## Use a codec for a different application value

A codec keeps encoding on writes and decoding on reads together. This field
stores a string while application code works with a bigint:

```ts
const counters = defineTable({
  value: v.string().codec({
    encode: (value: bigint) => value.toString(),
    decode: (value) => BigInt(value),
  }),
})
```

The storage validator still checks encoded data. Callbacks must be synchronous.
Null and omission handling remain explicit and bypass the codec as appropriate.
Inside JSON, declare conversions explicitly; a nested timestamp validator alone
does not make a Date JSON-safe.

Whole-value predicates encode application values. SQL text patterns and arithmetic
operate according to storage semantics, not arbitrary operations on your decoded
class or value. A string-backed bigint therefore does not become a numeric SQL
column. Choose the storage type around how you need to query it.

Declared function results also need a supported serializable contract. A custom
class returned from a direct server read is not automatically a browser wire type;
return an explicit supported value or use an output schema. SSR handoffs follow
your framework's serialization rules separately.
