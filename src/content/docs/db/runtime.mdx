The database service runs your queries and mutations and sends live results to the browser. Start it alongside your app and PostgreSQL when you use browser functions.

This page configures the service created in [Build a live task list](/guides/db/quick-start).

## Choose a command

| Command    | Effect                                                                     |
| ---------- | -------------------------------------------------------------------------- |
| `generate` | Creates typed entrypoints and service artifacts without opening a database |
| `init`     | Creates fresh storage or verifies an existing schema                       |
| `dev`      | Watches source, migrates its owned local database and reloads the service  |
| `migrate`  | Applies supported schema changes; `--check` previews without changing data |
| `serve`    | Verifies storage and runs prepared artifacts without a watcher             |
| `studio`   | Opens the optional local schema and data workbench                         |

With the [bundled development build](/docs/db/installation#local-development-requirements),
start local development from your app directory:

<DocsPackageManagerCommand
  commands={{
    bun: 'bun --bun hulla-db dev',
    npm: 'npx hulla-db dev',
    pnpm: 'pnpm exec hulla-db dev',
    yarn: 'yarn exec hulla-db dev',
  }}
/>

Commands default to `db.config.ts` in the current directory. An optional final
path selects another config. Your app's own development server runs separately.

## Let local schema changes reload automatically

With no `database.server.url` or `DATABASE_URL`, `dev` starts its bundled PostgreSQL,
initializes storage, generates bindings and starts the service. Local data persists
in `.hulla/postgres`; add `.hulla/` to your application's `.gitignore`.

Saving a supported schema change regenerates and validates the code, applies the
database migration and restarts the service. Adding a defaulted field fills existing
rows while preserving their IDs. No second command or manual restart is needed.
Unsupported changes or invalid function code stop that attempt and leave the watcher
waiting for a correction. Database contents are preserved.

Setting a server URL selects an external database. Run `init` once for fresh storage
and `migrate` when its schema changes; `dev` never provisions or migrates external
storage automatically. See [changing an existing schema](/docs/db/schemas#change-an-existing-schema) for
the supported changes and read-only preview.

Ctrl-C stops the service and its owned PostgreSQL process while preserving local
data for the next run. For an external database, only the service is stopped.

## Set the listener and browser origin

```ts filename="db.config.ts"
import { defineConfig } from '@hulla/db/config'

export default defineConfig({
  database: {
    server: {},
    client: { url: 'http://localhost:3001', credentials: 'include' },
  },
  service: {
    host: '127.0.0.1',
    port: 3001,
    origins: ['http://localhost:5173'],
  },
})
```

Host and port default to the values shown. Origins are exact HTTP(S) origins,
not wildcard patterns. The default empty list accepts requests without an Origin
header. Configure your browser application's origin for remote browser calls.
Production ingress needs HTTPS and unbuffered streaming responses.
Set `database.server.url` or `DATABASE_URL` when using your own PostgreSQL instance.

### Resolve an occupied port

When a CLI listener's address is in use, an interactive terminal offers the next available port, a custom address, or exit. Press Enter to choose the next available port. Without an interactive terminal, the CLI fails promptly; set `service.port` explicitly for automation.

Development remembers the selected address across worker reloads. When `database.client` is omitted, generation uses the actual development service address. An explicit `database.client` remains your public endpoint choice and is not rewritten when a local port changes.

## Inspect the database in Studio

Install the optional `@hulla/db-studio` package alongside the matching `@hulla/db` build, then start both tools together:

```sh
hulla-db dev --studio
```

Open the Studio access link printed in the terminal to explore the schema and browse or edit rows. Its listener defaults to `127.0.0.1:4983`; `--studio-port` chooses another port. Studio reloads with the development worker and retains its access token across reloads.

Use `hulla-db studio --read-only` to inspect an already running database separately. Standalone Studio loads the configured schema and connection without starting PostgreSQL, generating code, or starting the query service. See [Database Studio](/docs/db/studio) for access modes, row editing, and remote database connections.

## Connect browser functions

Put the public URL, credentials mode and optional timeouts in `database.client`.
Generation copies these settings into browser bindings; it never imports the server
config or credentials into the browser. A root-relative URL such as `/db` resolves
against the browser origin when calls start. Regenerate when changing environments.

Import generated callables directly. No startup call is required, and importing
modules opens no connection. On application teardown, call generated `dispose()`;
components release their subscriptions without disposing the shared runtime.

For authenticated calls, use the [authentication guide](/docs/db/authentication).
For framework startup and SSR, choose a [recipe](/docs/db/meta-frameworks).

## Use direct database calls on the server

Import `db` from `./db/_generated/server` in trusted application code. Authenticate
and authorize the request there; it does not need browser runtime setup.
See [read and write data](/docs/db/database) for builders and transactions.

## Set execution budgets

Defaults keep an individual invocation bounded. Raise the budget around a real
workload, rather than making every operation unbounded:

```ts filename="db.config.ts"
export default defineConfig({
  database: {
    server: { url: process.env.DATABASE_URL! },
    client: { url: 'http://localhost:3001', credentials: 'include' },
  },
  limits: { executionMs: 10_000, outputBytes: 24 * 1024 * 1024 },
})
```

Keep the `defineConfig` import from the earlier setup. A final query/mutation declaration can
override individual limits too; extensions cannot. Omitted settings inherit the
config, then the defaults in the [reference](/docs/db/reference#execution-limits).

The execution deadline covers server work, including lock waits and retries—not
the browser's upload/download time. Near-limit development diagnostics report
usage without logging submitted values. Exceeding a budget fails the operation
and prevents a mutation commit.

## Match browser deadlines to longer work

For a deliberately longer server operation, raise `database.client` deadlines
in `db.config.ts` before regenerating:

```ts
// Inside database.client:
{
  url: 'https://database.example.com',
  operationTimeoutMs: 60_000,
  queryTimeoutMs: 90_000,
  confirmationTimeoutMs: 90_000,
}
```

One-shot reads can retry interrupted transport within their overall deadline.
Mutation confirmation checks the submitted result and never resubmits the write.
Live reconnection is separate from replaying a handler failure. Defaults and the
stream-idle deadline are listed in the [reference](/docs/db/reference).

## Choose an application host

The app, persistent service and PostgreSQL can run together or separately. Keep
the same schema and generated artifacts on the server paths. See
[deployment](/docs/db/deployment) for native assets, connection lifecycle and
compatible hosting environments.
