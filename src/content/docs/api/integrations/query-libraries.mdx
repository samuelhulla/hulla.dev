title: 'Choosing a query cache'
description: 'Choose who owns browser cache and query state around an existing typed client.'
---

Choose who owns browser cache and query state around an existing typed `@hulla/api` client. The client already
performs transport, request encoding, response decoding, and status-discriminated results; add a query-library view
when the application also needs shared cache state, revalidation, or mutation state.

You can use the client directly when a framework loader or ordinary application function already owns that state:

| Choose                                                  | Best fit                                                                                      | Helper shape                                                                                                | Invalidation and cancellation                                                                                     |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| [TanStack Query](/docs/api/integrations/tanstack-query) | Shared cache, query/mutation state, and explicit `QueryClient` invalidation                   | `createTanStackQuery(client)` returns typed `queryKey()`, `queryOptions()`, and `mutationOptions()` helpers | Invalidate router-prefix keys with TanStack Query; its query function receives the query `AbortSignal`.           |
| [SWR](/docs/api/integrations/swr)                       | SWR's key, fetcher, revalidation, and `mutate` workflow                                       | `createSWR(client)` returns typed `[key, fetcher]` tuples plus mutation tuples                              | Revalidate or mutate the returned key with SWR; the helper does not provide an `AbortSignal` bridge.              |
| Plain typed client                                      | A route loader, framework data API, or local function already owns cache and lifecycle policy | Call the client route directly and handle its promise                                                       | Use the host data API for revalidation; pass an `AbortSignal` through the client call when the host provides one. |

## The shared mental model

Both integrations create a parallel, contract-shaped view over a client that already exists:

```ts
const query = createTanStackQuery(client)
const swr = createSWR(client)
```

They do not mutate `client`, add `$` properties, or run hooks during client creation. They also do not own the
transport, cache policy, retries, hydration, or framework lifecycle. The selected query library owns those policies;
the integration only derives typed keys and executable helpers from the client's route tree.

The helper must receive input for a route that declares request data. An input-free route can use
`queryOptions()` without an argument. In both views, `queryKey` is reserved as an integration name, so a contract
node with that name cannot be represented in the generated integration tree.

## Cache scope and response behavior

Pass a string-only `prefix` when separate clients share one query-library cache:

```ts
const query = createTanStackQuery(client, {
  prefix: ['service', tenantId, sessionVersion],
})
const swr = createSWR(client, {
  prefix: ['service', tenantId, sessionVersion],
})
```

`prefix` is a cache namespace, not a URL prefix. Include the tenant, authentication, or session scope needed to keep
entries separate, but never put credentials in a key. Recreate the integration when that scope changes and clear
sensitive cached data when the user signs out.

> A declared 4xx or 5xx response is data by default. Narrow `result.status` before reading its `body`; configure the
> client with `errorMode: 'throw'` only when named declared errors should reject instead. Operational, transport, and
> schema failures reject regardless.

Choose the focused guide for the cache owner you selected:

- [TanStack Query](/docs/api/integrations/tanstack-query) shows query and mutation options, cancellation, and prefix invalidation.
- [SWR](/docs/api/integrations/swr) shows key/fetcher tuples, mutation tuples, and revalidation.

For the underlying client call and response contract, see [client authoring](/docs/api/core/clients). For status,
declared-error, transport, and schema failure behavior, see [errors](/docs/api/core/errors).
