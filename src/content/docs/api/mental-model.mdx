`@hulla/api` has one shared description and two runtime halves. The contract types both halves, but it performs no I/O and contains no business logic.

<DocsApiArchitecture />

The client side asks for a route. The server side implements it. A transport and adapter meet in the middle to carry that call across the boundary your application actually has.

## Put each decision in one place

| File                            | Runtime     | Put this here                                                   |
| ------------------------------- | ----------- | --------------------------------------------------------------- |
| `src/api/contract.ts`           | Shared      | Paths, inputs, statuses, bodies, errors, schemas, and codecs    |
| `src/api/implementation.ts`     | Server only | Handlers, services, authorization, and server middleware        |
| `src/api/client.ts`             | Caller      | `createClient()`, client middleware, and the selected transport |
| Framework route or server entry | Host only   | Adapter mounting and native request context                     |

Share the contract with frontend code or publish it as a package. Keep the implementation server-only: it can access databases, secrets, queues, and framework state.

## Choose the middle boundary

| Your application needs…                            | Choose                                                                                          | What stays in your application                                          |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Calls inside a trusted server runtime              | [In-process](/docs/api/transports/in-process)                                                   | Server rendering, jobs, and tests; validation and middleware still run. |
| HTTP between browsers or services                  | [Fetch](/docs/api/transports/fetch)                                                             | Origin and deployment; the adapter matches Web requests.                |
| An existing framework router                       | A [native adapter](/docs/api/servers)                                                           | Routing, hooks, parsed bodies, response writing, and request context.   |
| A worker, desktop bridge, or persistent connection | [MessagePort](/docs/api/transports/message-port) or [WebSocket](/docs/api/transports/websocket) | The port or socket lifecycle. Client calls keep the same shape.         |

**Keep in-process clients on the server.** They import the server implementation and must never enter browser code.

## Validation follows direction

A request schema runs on the server after the transport decodes the request. A response schema runs on the server before the adapter sends the response.

The client does not rerun those ordinary schemas. If both sides should work with a richer value than the wire can carry—`Date` in memory and an ISO string in transit—use a codec with explicit encode and decode directions.

Type-only declarations skip application-shape validation altogether. They still use the selected representation, so malformed JSON remains malformed JSON; TypeScript alone does not make untrusted data safe.

## Four rules prevent most mistakes

- Keep framework imports, database clients, and secrets out of the contract module.
- Use ordinary functions when no contract boundary is needed.
- Treat declared non-`2xx` responses as expected values; reserve thrown failures for transport, schema, and unexpected runtime problems.
- Select the smallest contract subtree a client or server module needs.
