`@hulla/api` is for TypeScript teams that want the ergonomics of a typed RPC client without hiding HTTP.

Declare the API once. The server must implement every selected route, the client can call only what the contract exposes, and every declared status arrives with the right body type.

```ts filename="src/api/projects.ts" {5-12,16-18,24}
import { defineContract, request, response, route } from '@hulla/api'
import { createClient } from '@hulla/api/client'
import { inProcessTransport } from '@hulla/api/in-process'
import { defineServer } from '@hulla/api/server'

const contract = defineContract({
  routes: {
    createProject: route.post('/projects', {
      body: request.json<{ name: string }>(),
      responses: { 201: response.json<{ id: string; name: string }>() },
    }),
  },
})

const implementation = defineServer(contract).implement({
  createProject: ({ body, response }) =>
    response(201, { id: crypto.randomUUID(), name: body.name }),
})

const api = createClient(contract, {
  transport: inProcessTransport(implementation),
})

const result = await api.createProject({ body: { name: 'Documentation' } })
```

That small example already contains the whole model: a shared contract, a server implementation, a client, and one replaceable transport.

## Why use it?

### HTTP remains visible

Routes declare real methods, paths, request representations, response statuses, headers, and bodies. A `404` is not an exception-shaped afterthought—it is a response the client must handle.

This makes the contract useful beyond one UI. You can serve it to a browser, another service, an OpenAPI consumer, a worker, or a desktop bridge without redesigning the API around a procedure protocol.

### Your stack stays yours

Use native adapters for Express, Fastify, Hono, H3, Elysia, Koa, NestJS, Next.js, SvelteKit, Nuxt, Astro, serverless hosts, and more. The host keeps the things it is good at: routing, middleware, request context, streaming, and deployment.

On the calling side, choose Fetch, an in-process call, MessagePort, or WebSocket. Changing that boundary does not change `api.createProject(...)`.

### Runtime work is opt-in

Type-only declarations add no application-shape validation. When a boundary needs runtime checks, pass any [Standard Schema](https://standardschema.dev/) validator—Zod is one option, not a dependency or a requirement.

For values such as `Date` that look different in memory and on the wire, explicit codecs keep both directions visible.

### Drift fails early

Server implementations are exhaustive for the contract selection they implement. Rename a route, remove a handler, return an undeclared status, or send the wrong body and TypeScript points at the broken edge before a client discovers it in production.

## How it compares

These tools overlap, but they start from different sources of truth:

| Tool                                         | The source of truth               | It feels most natural when                                                         |
| -------------------------------------------- | --------------------------------- | ---------------------------------------------------------------------------------- |
| `@hulla/api`                                 | A standalone HTTP contract        | HTTP details matter and the same contract must cross different hosts or transports |
| [tRPC](https://trpc.io/)                     | A server procedure router         | One TypeScript application wants inference directly from its server implementation |
| [oRPC](https://orpc.dev/)                    | Procedures or a separate contract | You want its RPC/OpenAPI builders and broad procedure ecosystem                    |
| [ts-rest](https://ts-rest.com/)              | A standalone REST contract        | You want a contract-first REST client with its supported server integrations       |
| [Hono RPC](https://hono.dev/docs/guides/rpc) | A typed Hono route chain          | The server already belongs to Hono and clients should infer from that app          |

Choose `@hulla/api` when the boundary should outlive any one framework and when transport choice should remain explicit. If the API is only an internal function call, use an ordinary function. If a framework-owned typed client already matches every consumer, adding a separate contract may not buy you enough.

## One contract, a wider ecosystem

The core package covers contracts, clients, servers, Fetch, in-process calls, validation helpers, errors, and streams. Optional packages add only the boundary you need:

- native server and full-stack framework adapters;
- MessagePort and WebSocket transports;
- TanStack Query, SWR, and result-returning clients;
- OpenAPI import, export, and drift checks;
- serverless and edge runtime integrations.

No plugin registry sits in the middle. Each integration is an explicit package and an explicit import.
